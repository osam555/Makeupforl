# 25년 된 메이크업샵 홈페이지를 다시 짓다 — 메이크업포엘 구축 사례

> 압구정 메이크업포엘(makeupforl.co.kr) 홈페이지를 옛 PHP 사이트에서 새로 옮기며
> 손님용 화면, 유료 콘텐츠 '혼주 메이크업 100문100답', 관리자 대시보드와 방문 통계까지
> 만든 과정을 정리했습니다. 2026년 8월 초부터 9월 하순까지 약 7주, 커밋 300여 개의 기록입니다.

---

## 1. 출발점 — "검색에 걸리던 옛 사이트를 잃지 않고 바꾸기"

메이크업포엘은 대표원장님이 25년 동안 혼주·웨딩 메이크업을 해 온 압구정의 메이크업샵입니다.
기존 홈페이지는 오래된 PHP 사이트였습니다. 보기에는 낡았지만 네이버와 구글에 오래 쌓인
주소와 검색 순위가 있었고, 이것이 지금 손님이 들어오는 길이었습니다.

그래서 목표를 세 가지로 잡았습니다.

1. **옛 사이트의 얼굴과 검색 유입을 그대로 지킨다** — 새로 만들되 옛 주소로 들어온 손님이 길을 잃지 않게
2. **원장님의 25년 노하우를 상품으로 만든다** — 혼주 메이크업 100문100답
3. **원장님이 휴대전화로 사이트 상태를 직접 본다** — 대시보드, 방문 통계, 결재, 업무일지

## 2. 기술 선택 — 작은 가게에 맞는 구성

| 구분 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js 16 (App Router) + React 19 | 페이지를 미리 그려 두어 검색엔진이 읽기 쉽고 빠르다 |
| 디자인 | Tailwind CSS v4 + shadcn 스타일 컴포넌트 | 관리자 화면을 빠르게 짤 수 있다 |
| 데이터 | Firebase (Firestore · Storage · 구글 로그인) | 서버를 따로 운영하지 않아도 된다 |
| 배포 | Vercel 서울 리전(icn1) | 국내 손님 기준으로 가장 가깝다 |
| 음성 | edge-tts(원장님 목소리 역) · Typecast(진행자) | 100문100답을 '듣는 콘텐츠'로 |

처음에는 Supabase 로 시작했다가 2026년 8월 5일 Firebase 로 전부 옮겼습니다. 구글 로그인과
파일 저장, 데이터베이스를 한곳에서 해결할 수 있었기 때문입니다.

### 이 사이트의 가장 중요한 원칙: "데이터베이스가 죽어도 화면은 산다"

데이터를 읽을 때는 언제나 같은 순서를 탑니다.

1. 서버용 관리자 SDK 로 Firestore 를 읽는다
2. 안 되면 브라우저용 SDK 로 읽는다
3. 그것도 안 되면 저장소에 들어 있는 **시드 JSON** 을 보여 준다

Firebase 설정이 하나도 없어도 사이트 전체가 뜹니다. 장애가 났을 때 화면이 비는 것이
옛 내용이 잠깐 보이는 것보다 손해가 훨씬 크기 때문입니다. 관리자 화면에서 고친 내용은
스크립트로 시드에 되돌려 넣어, 장애 때 보이는 내용도 최신에 가깝게 유지합니다.

## 3. 옛 사이트 이식 — 치수까지 맞추기

- 옛 사이트의 CSS 를 그대로 가져와 손님 화면에만 적용하고, 실측 치수에 맞춰 다시 다듬었습니다.
- 갤러리 사진 136장, 고객후기 25건(문자 캡처), 인스타그램 게시물 48개를 옮겼습니다.
- 후기 이미지는 글로 옮겨 22건을 텍스트로 싣고, 갤러리 사진 46장에는 실제 설명(alt)을 달았습니다.
  사진만 있던 페이지는 검색엔진 입장에서 "없는 것과 같았기" 때문입니다.
- 50대 이상 손님이 많아 작은 글씨를 키우고 회색 글자 대비를 높였으며, 화면마다
  글자 크기 단추(가·가·가)와 어두운 테마를 붙였습니다.

## 4. 핵심 상품 — 혼주 메이크업 100문100답

혼주(신랑·신부의 어머니)가 결혼식을 앞두고 묻는 질문 100개에 원장님이 답한 콘텐츠입니다.
주소는 `/honjoo100` 입니다.

- **듣는 콘텐츠**: 진행자가 질문을 읽고 원장님 목소리 역이 답을 읽습니다. 두 음성을 이어 붙이기
  때문에 음질 규격(24kHz · 48kbps · 모노)을 반드시 맞춥니다. 어긋나면 자막 시간이 밀립니다.
- **자막**: 본문을 고치면 자막도 따라 바뀌고, 한글 / 한글+English 를 고를 수 있습니다.
  재생 속도는 2배속까지, 선택은 기억됩니다.
- **유료 잠금**: 다섯 문항은 무료, 나머지는 이용권(55,000원)을 산 분이 구글 로그인이나 이메일
  링크로 3개월 동안 엽니다. 설정을 못 읽는 상황에서는 **잠그지 않는 쪽**으로 동작합니다.
- **잠긴 화면도 파는 화면으로**: 제목만으로는 읽고 싶어지지 않아서 맛보기 문장, 값, 카카오
  채널 문의 단추를 넣었습니다.
- **버전 관리**: 답변을 저장할 때마다 직전 내용이 남아, 날짜로 보고 날짜로 되돌릴 수 있습니다.

## 5. 검색 유입 지키기와 키우기 (SEO)

옮기는 과정에서 유입을 잃지 않는 것이 가장 큰 숙제였습니다.

- **옛 주소 76건 301 리다이렉트** — 처음엔 308 로 걸었다가, 네이버가 새 내용을 긁고도 옛 주소로
  두는 것을 보고 301 로 바꿨습니다.
- **검색어 허브** — 사람들이 실제로 치는 말을 그대로 주소로 씁니다. `/혼주한복`, `/혼주머리`,
  `/혼주메이크업`. 허브 본문은 100문100답의 답을 그대로 옮기지 않습니다 — 유료 상품이 남아야 하니까요.
- **사업장 정보·저자·정본 주소를 구조화 데이터로**, 네이버 웹마스터도구 소유확인, 사이트맵·robots.
- **속도**: 글꼴 Pretendard 를 가변 서브셋으로 바꿔 5.3MB 를 수백 KB 로 줄였고, 첫 화면을 늦추던
  CSS 덩어리를 정리했습니다. 배경 이미지도 WebP/AVIF 로 자동 변환되게 했습니다.
- **CEO 칼럼 13편** — 상견례, 출장, 60대 피부, 헤어 같은 긴 꼬리 검색어를 맡는 글을 1,500~1,700자,
  소제목 5개 이상으로 쓰고, 칼럼과 100문100답 문항을 서로 링크로 엮었습니다.

## 6. 관리자 대시보드 — "숫자를 보고 나서 무엇을 할지 알게"

관리자 화면(`/admin`)은 구글 계정으로만 들어갑니다. 처음에 두었던 비밀번호 로그인은 보안
문제로 없앴습니다. 원장님이 휴대전화 홈 화면 아이콘으로 바로 여는 것을 기준으로 만들었습니다.

탭은 열 개입니다: **대시보드 · 결재 · 업무일지 · 키워드 · 방문 · 100문100답 · CEO 칼럼 · 영상 · 문항 통계 · 예약**

### 대시보드는 세 층

1. **한눈에** — 지금 어떤 상태인가. 숫자 여섯 개
2. **할 일** — 그래서 무엇을 하면 되는가. 효과가 큰 것부터
3. **섹션별** — 왜 그런가. 방문 · 검색 · 콘텐츠 · 판매

숫자만 늘어놓으면 보고 나서 무엇을 해야 할지 모릅니다. 그래서 '할 일'을 가운데 두었습니다.

### 시니어도 읽히는 관리 화면

글자 크기는 일반 / 크게 / 아주 크게 세 단계이고 기본은 '크게'입니다. 탭이 휴대전화 폭을 넘으면
옆으로 밀고, 지금 있는 탭은 자동으로 화면 가운데로 끌어옵니다.

## 7. 방문 통계 — 사람을 식별하지 않고 세기

Vercel 웹 통계도 쓰지만, 원장님이 궁금한 것은 "어디서 와서 어느 페이지로 들어왔나" 였습니다.
그래서 자체 방문 기록(2026-09-09 부터)을 따로 쌓습니다.

- **개인정보를 남기지 않습니다.** 쿠키·IP·브라우저 정보를 저장하지 않고, 날짜별 문서 하나에
  방문 수·조회 수·체류 시간·출처별 숫자만 더합니다.
- **출처를 잘게 나눕니다.** 네이버는 모바일·PC·플레이스·블로그로, 그리고 출처별로 어느 페이지에
  처음 들어왔는지까지 셉니다.
- **봇은 세지 않습니다.** 검색 로봇·자동 브라우저는 판별만 하고 숫자에서 뺍니다. 그 뒤로 네이버·구글
  유입 숫자가 Vercel 통계와 3~5% 안에서 맞습니다.
- **"직접 방문"의 진짜 뜻**: 주소 직접 입력뿐 아니라 카카오톡·문자·인스타 DM 링크로 들어온 분도
  여기 잡힙니다. 앱 안의 브라우저가 출처를 붙이지 않기 때문입니다. 숫자를 읽는 법을 화면에 함께 적었습니다.
- 화면에서는 **일 · 주 · 월** 단위를 오가고, 표의 행마다 출처 비중 막대를 그려 숫자보다 먼저 비율이
  보이게 했습니다. 요약 카드는 오늘·이번 주·이번 달을 바로 앞 기간과 나란히 보여 줍니다.
- **문항 통계** 탭에서는 100문100답 문항별 조회·재생·끝까지 듣기·문의 단추 클릭을 7/30/90일로 봅니다.

## 8. 키워드 화면 — 순위가 아니라 "준비도"

검색 순위는 우리가 정할 수 없지만, 순위를 올리기 위해 할 수 있는 일은 잴 수 있습니다.

- 키워드 13개마다 맡는 페이지가 있는지, 본문이 충분한지, 여러 페이지가 같은 말을 두고 다투지
  않는지, 내부 링크가 몇 개인지를 계산해 **준비도**로 보여 줍니다.
- 내부 링크 수는 처음엔 "무조건 4"로 놓았다가, 실제로 세어 보니 세 페이지 모두 틀린 값이어서
  스크립트로 실측하도록 바꿨습니다. 계산 방식이 바뀌면 판 번호를 붙여, 서로 다른 판의 숫자를
  같은 줄에 두고 비교하지 않게 했습니다.
- 실제 순위는 검색 결과를 긁지 않고 사람이 재서 날짜와 함께 적습니다(검색엔진 약관, 그리고
  기기·위치마다 값이 달라서). 1·2·4주 추세를 그리고, 오래된 값은 오래됐다고 표시합니다.

## 9. 결재와 업무일지 — 원장님과 매니저가 일하는 방식을 화면으로

관리자는 두 명입니다. 원장님은 **결재**, 사이트 매니저는 **제안**을 맡습니다.

- 누구든 **요청**(하고 싶은 말)을 올리면 서버가 반대편 앞으로 보냅니다. 원장님이 최종 문장까지
  쓸 필요는 없습니다 — 그러면 요청 자체를 안 하게 되니까요.
- 받은 사람이 **승인하면 그대로 쓰일 최종 문장**을 붙여 제안으로 만들고, 원장님이 승인 · 반려 ·
  **의견 남기고 보류** 중에서 고릅니다. "좋은데 이 낱말만"이 가장 흔해서 보류를 따로 두었습니다.
- 승인되면 데이터베이스에 있는 내용은 즉시 반영되고 직전 내용이 남습니다. 코드에 있는 내용은
  "올려도 좋다"는 표시만 남기고 배포는 사람이 합니다 — 반영 안 된 승인을 반영된 척 보이지 않게.
- **업무일지**에는 무엇을 했는지 원장님이 읽는 말로 남습니다. 파일 이름이 아니라 "홈 화면 후기
  카드를 글로 바꿨습니다" 같은 문장으로, 작업 커밋과 함께 기록합니다(현재 36건).

## 10. AI 코딩 에이전트와 함께 만든 방식

이 프로젝트의 커밋 300여 개 가운데 60여 개는 AI 코딩 에이전트(Claude Code)가 직접 작성했고,
나머지 작업도 상당 부분 에이전트와 대화하며 만들었습니다. 잘 굴러간 비결은 세 가지였습니다.

1. **저장소에 규칙을 글로 남긴다.** `CLAUDE.md` 에 "데이터베이스가 없어도 사이트는 떠야 한다",
   "비밀번호 로그인은 되살리지 말 것", "옛 주소 리다이렉트를 지우면 유입이 사라진다" 같은 원칙을
   적어 두니, 새 작업에서도 같은 실수를 반복하지 않았습니다.
2. **'왜'를 주석과 커밋에 남긴다.** "308 → 301, 네이버가 옛 주소로 두고 있었다"처럼 무엇이 깨졌고
   왜 바꿨는지를 적어, 다음 사람(사람이든 에이전트든)이 같은 길을 다시 헤매지 않게 했습니다.
3. **사람이 결재하고, 원장님 말로 보고받는다.** 에이전트가 만든 변경도 결재함과 업무일지를 거쳐
   원장님 눈에 보이는 말로 정리됩니다.

## 12. 돌아보며 — 작은 가게 홈페이지에서 배운 것

- **옛 사이트의 주소는 자산이다.** 디자인은 바꿔도 주소는 지킨다.
- **장애 때 빈 화면보다 옛 화면이 낫다.** 폴백을 처음부터 설계한다.
- **통계는 행동으로 이어져야 한다.** 숫자 → 할 일 → 이유 순서로 보여 준다.
- **사장님이 쓰는 화면은 사장님 기준으로.** 큰 글씨, 휴대전화, 결재 단추 하나.
- **개인정보는 안 모으는 것이 가장 안전하다.** 세기만 하고 사람은 알아보지 않는다.
